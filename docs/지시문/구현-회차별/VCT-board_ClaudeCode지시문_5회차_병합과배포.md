[VCT-board 상세 페이지 구현 — 5회차 / 5]

[역할과 목표]
너는 VCT-board(발로란트 VCT LFT·FA 현황 GitHub Pages 정적 사이트, 저장소 4nhackle/VCT-board)에 선수·팀 상세 페이지를 추가하는 구현을 맡았다. 전체 구현은 5회차로 나뉘어 있고 이번은 5회차다. 이 세션에서는 이번 회차 범위만 구현하고, 다음 회차 작업은 미리 하지 마라.

[먼저 읽을 것]
- docs/ 의 설계 문서 4개(.docx). pandoc -t markdown 으로 읽는다. 문서가 없으면 구현을 시작하지 말고 사용자에게 알려라.
  · VCT-board_사이트코드_변경설계서.docx : 전체 설계 (이번 회차에 해당하는 장은 아래에 적었다)
  · VCT-board_구현체크리스트.docx : 작업 ID, 완료 기준, 선행 작업, 확인 항목(V-xx)
  · VCT-board_설계노트.docx : 작업 ID별 상세 설계
  · VCT-board_예약작업_변경설계서.docx : 참고용(이번 구현 범위 아님). 예약 작업이 매일 data/*.json 을 main에 커밋한다는 점만 기억한다.
- docs/PROGRESS.md : 이전 회차의 완료 작업, 결정·변경, 넘겨받은 주의점. 가장 먼저 읽는다.
- 기존 코드(js/, css/, scripts/validate.mjs, index.html)와 data/*.json 의 구조를 직접 읽고 기존 규칙을 확인한다.

[지킬 규칙]
1. 브랜치: feature/detail-pages 에서만 작업한다. main 에 직접 push 하지 않는다(병합은 5회차에서 사용자 승인 후). 회차를 시작할 때 git fetch origin 후 git rebase origin/main 을 한다(예약 작업이 매일 main 에 데이터를 커밋하므로). data/ 에서 충돌이 나면 main 쪽을 따른다.
2. 하위 호환: 지금의 data/ 만으로(people.json, teams.json, 새 필드가 없어도) 사이트가 지금과 똑같이 동작해야 한다.
3. 건드리지 않는 것: data/*.json 의 기존 내용, og.png, index.html(수정이 필요하다고 판단되면 멈추고 사용자에게 묻는다), 기존 필드 이름, toItem() 이 지금 돌려주는 필드.
4. 코드 규칙: 기존 코드와 같은 스타일(바닐라 ES 모듈, var·function 스타일, 한국어 주석). 빌드 도구, package.json, 외부 라이브러리를 추가하지 않는다. model.js 는 DOM·state 를 만지지 않는 순수 함수만 둔다. HTML 문자열에 들어가는 데이터는 모두 esc() 로 이스케이프한다.
5. 설계와 맞지 않는 상황을 발견하면 설계를 임의로 바꾸지 말고, 가장 작은 변경으로 해결한 뒤 docs/PROGRESS.md 의 "결정·변경" 에 이유와 함께 적는다. 설계 전체에 영향이 크면 멈추고 사용자에게 묻는다.
6. 작업은 체크리스트의 선행 관계 순서로 한다. 작업 하나를 끝내면 완료 기준을 직접 실행해 확인하고, 통과했을 때만 완료로 표시하고 커밋한다. 커밋 메시지는 "S1-02 인덱스 생성: ..." 처럼 작업 ID로 시작하는 한국어 한 줄로 쓴다.
7. 브라우저 확인은 저장소 밖 임시 폴더(예: /tmp/vct-check)에 Playwright 를 설치해 실행한다. 저장소에 package.json, node_modules, 캡처 파일을 남기지 않는다.
8. 확인하지 못한 것을 "확인함"이라고 쓰지 않는다. 못 한 것은 이유와 함께 못 했다고 보고한다.

[회차를 끝낼 때]
- docs/PROGRESS.md 를 갱신해 커밋한다: 완료한 작업 ID, 변경한 파일, 통과한 확인 항목, 결정·변경, 다음 회차가 알아야 할 점.
- git push origin feature/detail-pages 로 올린다.
- 사용자에게 한국어로 짧게 보고한다: 완료·미완료 작업 ID, 확인 결과, 사용자가 판단하거나 직접 해야 할 일.

[이번 회차 범위] 작업 S3-06, S4-01, S4-02, S4-03. 이 회차는 main 과 실제 사이트에 영향을 주므로, 아래 [멈춰서 사용자에게 확인받을 지점] 에서는 반드시 멈춘다.

- git fetch origin, git rebase origin/main 으로 최신 main 위에 올린다.

[할 일]
1. 병합 전 전체 점검: node scripts/validate.mjs(현재 data/), node scripts/build.mjs(현재 data/ 와 샘플 fixtures 둘 다), 로컬 _site 로 V-01~V-04, V-08, V-10(샘플 기준)을 다시 실행한다. 결과를 PROGRESS.md 에 적는다.
2. S4-01 PR 만들기: gh pr create 로 feature/detail-pages → main PR 을 만든다. 본문에는 변경 요약, 작업 ID별 완료 현황, 확인 결과, 알려진 제한(아래)을 쓴다.
   [멈춰서 사용자에게 확인받을 지점 ①] 병합 시각과 방식. 다음 시각의 앞뒤 30분은 피하도록 안내한다: 매일 08:50(시트 갱신), 09:35(웹 반영) KST, 그리고 11/2~11/16 의 14:50, 15:35, 20:50, 21:35 KST. 병합 방식은 사용자가 정한다(기본 제안: 작업별 커밋이 남는 merge commit). 사용자가 승인하기 전에는 병합하지 않는다.
3. 병합 후 S3-06: Claude Code 는 저장소 설정을 바꿀 수 없다. 사용자에게 안내한다: 저장소 Settings → Pages → Build and deployment → Source 를 "GitHub Actions" 로 바꾼다. 병합 직후 자동으로 도는 워크플로의 deploy 단계는 아직 Pages 설정이 전환되기 전이라 실패할 수 있다. 이는 예상된 동작이며(기존 사이트는 그대로 유지된다), 전환 후 4번에서 다시 돌린다.
   [멈춰서 사용자에게 확인받을 지점 ②] 사용자가 설정을 바꿨다고 알리면 다음으로 간다.
4. 첫 배포: gh workflow run pages.yml --ref main 후 gh run watch 로 끝까지 본다. 실패하면 원인을 보고하고 고친다(수정은 새 브랜치와 PR 로 한다. main 에 직접 push 하지 않는다).
5. 실제 사이트(https://4nhackle.github.io/VCT-board/) 확인: V-01~V-04, V-10(팀 이름 기반 임시 ID 주소로 404 대체 진입 포함). V-05~V-07 은 샘플 결과로 갈음한다고 적는다. V-08 은 아직 people 데이터가 없어 실제 사이트에서 확인할 수 없다고 적는다(예약 작업 전환 후 첫 웹 반영 다음에 확인).
6. S4-02 문서 커밋: docs/ 의 docx 4개를 커밋하고 PROGRESS.md 를 최종 상태로 갱신하는 작은 PR 을 만들어 병합한다(사용자 승인 후). 웹 반영 예약 작업의 수정 금지 범위에 docs/ 가 들어가므로 예약 작업이 건드리지 않는다.
7. S4-03 예약 작업 전환 준비: 사이트가 새 필드와 people·teams 를 받을 준비가 됐음을 PROGRESS.md 에 정리하고, 사용자에게 다음 단계(시트에 인물·팀 탭 추가와 기존 인원 채우기, 예약 작업 4개 지시문 변경 — 예약 작업 변경 설계서 8장 2~4번)를 알린다. 시트와 예약 작업은 이번 구현 범위 밖이므로 직접 건드리지 않는다.

[알려진 제한 — PR 과 최종 보고에 적는다]
- 병합 직후 data/ 에는 people·teams 가 없어 인물·팀 상세는 현재 소식에서 가져온 정보만 보이고, 정적 페이지(p/, t/)는 만들어지지 않는다. 공유 미리보기는 people 데이터가 생긴 뒤부터 선수 이름으로 나온다.
- 상세 주소는 정적 페이지가 없으면 404.html 대체로 열리므로 이때는 HTTP 상태가 404 로 보일 수 있다.
