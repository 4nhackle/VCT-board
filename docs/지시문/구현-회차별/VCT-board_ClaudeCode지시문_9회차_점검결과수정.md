## F-01. 인물·팀 상세에서 보도 시각이 두 번 나온다 (먼저)

- **위치**: `js/views/common.js`의 `newsRow()`. `when` 을 만드는 줄(약 63행)이다.
- **현재**: `relDate(it.date) + (stampLabel(it) ? " " + stampLabel(it) : "")`
  - 출처 줄(`srcsHTML`)에도 같은 시각이 나와서 두 번 보인다.
  - 예: 비고 "(Sheep 10/24 16:30 UTC)", 날짜 10/25 → 날짜 줄 "10/25 · 오전 1:30" + 출처 줄 "보도 Sheep 10/25 오전 1:30"
- **수정**: 목록(`js/components/row.js` 약 44행)과 같은 조건으로 바꾼다. `stampLabel(it) && !sp.src`일 때만 날짜 줄에 붙인다.
  - `sp`가 `when`보다 뒤에 계산되면 순서를 바꾼다.
- **확인**: 위 예시 비고를 가진 샘플 행으로 `newsRow` 출력을 확인한다. 시각이 출처 줄에만 한 번 나와야 한다. 출처 표기가 없는 비고는 지금처럼 날짜 줄에 시각이 남아야 한다.

## F-02. 이름이 "-"인 행이 없는 주소로 링크된다

- **위치**: `js/model.js`의 `idsOf()`(약 70~82행), `cleanName()`(약 250행)
- **현재**: `cleanName`은 "-"를 빈 값으로 보지만 `idsOf`는 이를 쓰지 않는다. 그래서 `slugOf("-")`가 `x-<해시>`를 만들고, 이름 링크가 없는 `p/x-…/`를 가리킨다.
- **수정**: `idsOf`에서 인물 ID와 팀 ID를 만들 때 모두 `cleanName`을 거친다.
  - 인물: `r.personId || (cleanName(r.name) ? slugOf(cleanName(r.name)) : "")`
  - 팀: `tidOf()`의 이름 인자
  - 지켜볼 팀: `team.split(" / ")` 결과에도 `cleanName`을 적용하고 빈 값은 걸러 낸다.
- `cleanName`은 같은 모듈의 함수 선언이라 위치와 상관없이 쓸 수 있다. 그대로 둔다.
- **확인**: 이름 "-", 팀 "-"인 행에서 `pid`/`tid`가 빈 문자열이고 링크가 만들어지지 않는다. 지금 데이터에는 "-" 이름이 없으므로 `_site` 결과는 같아야 한다.

## F-04. 시각을 읽는 코드가 두 벌이다

- **위치**: `js/views/common.js`의 `STAMP_RE`·`splitNote()`(약 23행), `js/format.js`의 `stampOf()`(약 20행)
- **현재**: 둘 다 "M/D HH:mm UTC|KST"를 따로 읽는다. 날짜 칸과 같은 날인지는 `stampOf`만 확인한다.
- **수정**: `js/format.js`에 공통 함수 하나를 둔다.
  - 이름: 예 `parseStamp(text)` → `{ mon, day, hh, mm, tz }` 또는 `null`
  - 범위 확인(월 1~12, 시 <24, 분 <60)과 KST 환산(UTC+9)까지 이 함수가 한다.
  - `stampOf`와 `splitNote`가 이 함수를 쓴다.
- **유지할 차이**: `splitNote`는 끝의 괄호 "(출처이름 …)" 모양에서 출처 이름까지 떼어 내야 한다. 괄호 패턴은 `splitNote`에 남긴다. 숫자 해석과 환산만 공통 함수로 옮긴다.
- **화면 동작은 바꾸지 않는다.**
  - 날짜가 맞지 않을 때 출처 줄에 시각을 보여 주는 지금 동작은 그대로다.
  - 날짜 옆 표시는 `stampOf`의 날짜 확인을 따른다. 이것도 그대로다.
- 줄 수가 줄어야 한다(점검 추정 약 -8줄). 늘었다면 이유를 적는다.
- **확인**:
  - `stampOf`의 기존 시험이 통과한다.
  - 기준선 대비 `_site`에서 F-01 외 차이가 없다.
  - 아래 F-06의 시험이 통과한다.

## F-05. 철자만 다른 두 이름이 같은 사람으로 합쳐진다 (경고만)

- **위치**: `scripts/validate.mjs`, 근거는 `js/model.js`의 `slugOf()`
- **현재**: "ZYZZ"와 "zyzz"처럼 대소문자·악센트·기호만 다른 이름이 같은 ID가 된다. 그러면 경력과 소식이 한 페이지로 합쳐진다. 검증은 완전히 같은 이름만 잡는다.
- **수정**: 검증에 경고를 추가한다.
  - `personId`가 없는 행을 모은다. 대상은 players, coaches, transfers의 선수·코치 구역, watch의 인물 이름이다.
  - 이 행들의 원래 이름을 `slugOf`별로 묶는다.
  - 서로 다른 원래 글자가 둘 이상이면 경고한다.
  - 경고 예: "인물 이름 'ZYZZ'(players 3행), 'zyzz'(transfers 12행)가 같은 ID 'zyzz'가 됩니다. 같은 사람이면 표기를 맞추고, 다른 사람이면 인물ID를 따로 지정하세요"
  - 팀 이름(`teamId` 없는 행의 팀 칸)도 같은 방식으로 경고한다.
  - people.json이 있으면 그 이름과 별칭(aliases)도 함께 대조한다.
- 오류가 아니라 경고다. 종료 코드와 동작은 바꾸지 않는다.
- 같은 사람이 여러 탭에 같은 글자로 나오는 것은 정상이다. 경고하지 않는다.
- **확인**: 현재 data/로 실행해 새 경고가 몇 건인지 보고한다. 0이 아니면 목록을 그대로 붙인다(데이터는 고치지 않는다).

## F-06. 핵심 규칙에 직접 시험이 없다

`scripts/test.mjs`에 작은 시험을 추가한다. 지금 동작을 그대로 고정하는 시험이다. 기준일은 기존처럼 인자로 고정한다.

- **`stampOf`**
  - 날짜 칸과 같은 날 → 분 값을 낸다.
  - UTC 16:30이 KST로 다음 날이 되는 경우 → 날짜 칸이 다음 날이면 값을 내고, 전날이면 `null`이다.
  - 연말과 연초 경계(12/31 ↔ 1/1).
- **`parseStamp`**(F-04): 범위 밖 값(13/1, 24:00, 10:60)은 `null`이다.
- **`splitNote`**: 출처 이름과 시각 분리, "교차 확인: A, B" 분리, 규칙에 맞지 않는 글은 body에 원문 그대로 남는다.
- **`newestFirst`**
  - 날짜가 다른 경우의 순서.
  - 같은 날 시각 있는 행과 없는 행의 순서.
  - 같은 날 같은 시각일 때의 동률 처리. 동률 처리는 지금 코드가 하는 그대로 고정한다.
- **`idsOf`**
  - "ZYZZ"/"zyzz"가 같은 ID가 되는 지금 동작을 고정한다. 시험 이름에 "의도된 현재 동작, F-05 경고로 감시"라고 적는다.
  - "-" 이름에서 빈 ID(F-02).
  - `personId`/`teamId`가 있으면 이름보다 우선한다.
  - `teamIds`가 문자열일 때(R-05).
- **`matches`**(검색): 대소문자 무시, 악센트 무시(지금 동작대로), 팀 이름으로 찾기.
- **`fmtDate`**: 일련번호 → "M/D".
- **F-01**: `newsRow` 출력에 같은 시각 글자가 한 번만 나온다.

## F-07. 배포 워크플로의 액션을 커밋 SHA로 고정

- **위치**: `.github/workflows/pages.yml`의 `uses:` 4곳
  - `actions/checkout@v4`
  - `actions/setup-node@v4`
  - `actions/upload-pages-artifact@v3`
  - `actions/deploy-pages@v4`
- **수정**: 각 액션을 지금 그 태그가 가리키는 커밋의 전체 40자 SHA로 바꾼다. 줄 끝에 `# v4.x.y` 주석으로 버전을 남긴다.
  - SHA는 `git ls-remote https://github.com/actions/<이름> 'refs/tags/v*'`로 확인한다.
  - 주석 태그면 `^{}` 줄의 커밋 SHA를 쓴다.
  - 메이저 태그(v4)가 가리키는 커밋과 같은 정확한 버전 태그(v4.x.y)를 찾아 주석에 쓴다.
- 다른 설정(권한, concurrency, 조건)은 바꾸지 않는다.
- **확인**:
  - 이 브랜치 push에서 Actions의 build job(시험·검증·빌드)이 success다. main이 아니면 deploy는 돌지 않는 것이 정상이다.
  - 4개 SHA와 버전 표를 보고에 적는다.
- 나중에 버전을 올리는 방법(Dependabot 등)은 추가하지 않는다. 보고에 제안으로만 적는다.
